# 离线演示数据与验收

## CSV 规范 `zhuru-wave-v1`

从文件第一行起，固定列为 `meta_key,meta_value,sample_index,X_raw[,Y_raw,...]`。
元数据占最初若干行，仅填写前两列，采样行仅填写索引及各通道的原始码值：

```csv
meta_key,meta_value,sample_index,X_raw
format,zhuru-wave-v1,,
sample_rate_hz,,,
channel_count,1,,
channel_names,X,,
amplitude_unit,raw,,
mode,DEMO,,
scenario,mixed,,
source,60x1.csv,,
,,0,20625.3
,,1,18750.3
,,2,17500.3
```

样本索引从 0 开始，连续、等间隔；多通道行必须**在同一采样时刻**对应。原始码值不是伏特，若不知道采样率就把 `sample_rate_hz` 留空。现场 DRC 风格的 TSV（含三行头部）和历史单列、双列 CSV 也可被现有导入按钮兼容读取。

## 构造演示数据

用 `60x1.csv` 的**未修改现场底稿**叠加用户上传的异常形状模板：

```powershell
python scripts/generate_demo_data.py --source C:\field_data\60x1.csv --templates algorithm_experiments\test_data --output C:\demo
```

生成 **7 份各 60,000 点** 的 CSV（可以通过 `--sample-count N` 调整，要求 N≥20,000）和 `labels.json`。单项异常文件包含两段相互分开的故障；混合异常包含五种故障。第一份文件的含义是 **未注入模拟缺陷**，并不是经过工艺认证的“绝对正常”样本。生成时不填未知的实际采样率。

`labels.json` 仅用于测试统计，**绝不能发送给 detector 或用于强制触发报警**。

## 实际播放路径

原来的 **通道详情 → 导入本地数据** 按钮不变。顺序读取 2000 点一批，等待每次 Python 检测返回，然后显示该批波形、标记异常并触发旧报警系统；检测服务异常与物理波形报警分开。回放完成后停留在最后一帧，不自动重新启动采集卡。实时采集 Worker 保持原本异步执行策略。

## 60,000 点样本的初步回归结果

每份文件按 2,000 点切窗，用 `backend/detector.py` 实际检测（默认灵敏度 1.0）：

| 数据 | 人工注入区间数 | 检出区间数 | 不匹配注入标签的检测事件数 |
| --- | ---: | ---: | ---: |
| 未注入底稿 | 0 | — | 3 |
| 毛刺 | 2 | 1 | 3 |
| 削波 | 2 | 2 | 3 |
| 圆顶 | 2 | 2 | 3 |
| 顶峰突降 | 2 | 1 | 3 |
| 零点台阶 | 2 | 2 | 3 |
| 混合异常 | 5 | 4 | 3 |

这说明**数据延长后原底稿也可能产生报警**。未匹配事件不能直接当成虚报，因为底稿本身尚未经过人工真值确认；同样不能把未注入部分标记为已认证正常。测试结果不等于现场工艺准确率。必要时使用新的现场正常标定数据改进检测算法，不能为了演示读取 `labels.json` 伪造报警。

如果导入数据只显示波形不报警，先检查 Python 服务 `GET http://127.0.0.1:5001/health` 是否返回 `status: ok`。离线检测服务不可用时，应停止导入并明确提示，而不是把检测失败当作“正常”。
